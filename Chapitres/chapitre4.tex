\subsection{Priorités MoSCoW}

Chaque user story est priorisée selon la méthode MoSCoW, qui permet de séparer l'essentiel de l'accessoire et d'éviter que des fonctionnalités secondaires ne retardent la livraison du cœur du système.

\begin{itemize}[label=•]
    \item \textbf{M — Must Have} : fonctionnalités sans lesquelles le système ne peut pas remplir son objectif. Leur absence rendrait le projet inutilisable pour le service RI.
    \item \textbf{S — Should Have} : fonctionnalités importantes, mais dont le report à une version suivante reste acceptable sans compromettre le MVP.
    \item \textbf{C — Could Have} : fonctionnalités souhaitables, planifiées uniquement si la capacité restante du sprint le permet une fois les priorités supérieures traitées.
    \item \textbf{W — Won't Have} : fonctionnalités explicitement exclues du périmètre actuel, documentées pour ne pas créer d'attente non maîtrisée.
\end{itemize}

\section{Approches de conception : organisation du code et style architectural}
% ─────────────────────────────────────────────────────────────

Avant de détailler l'architecture technique, deux décisions structurantes doivent être présentées : l'approche retenue pour organiser le code, et le style architectural choisi pour l'ensemble du système.

\subsection{Organisation du code : Domain-Driven Design allégé}

Le système est structuré selon les principes du \textit{Domain-Driven Design}
(DDD), une approche qui consiste à organiser le code autour des domaines métier
plutôt qu'autour de considérations techniques.

\subsubsection{Découpage en domaines métier}

Le système est décomposé en domaines indépendants, chacun correspondant à une
fonction distincte de la gestion de la mobilité. Ce découpage garantit qu'une
modification dans un domaine n'affecte pas les autres.

\begin{table}[H]

\subsubsection{Langage commun}

Le DDD préconise l'adoption d'un vocabulaire métier commun, partagé entre la développeuse et l'experte du domaine. Les noms des classes et des méthodes reprennent directement le vocabulaire du service RI ce qui facilite les échanges et réduit les risques d'ambiguïté lors de la validation des fonctionnalités.

\subsubsection{Encapsulation des règles métier}

Chaque domaine encapsule ses propres règles métier, ce qui permet de les faire
évoluer indépendamment du reste du système.
Cette séparation rend le système plus robuste face aux évolutions de besoins,
inévitables dans un contexte de développement itératif où certaines règles —
comme les critères de priorité dans l'affectation — se précisent au fil des
sprints.

\subsection{Style architectural : architecture en couches}

Le système est structuré selon une architecture en couches, où chaque niveau a une responsabilité clairement délimitée. Ce style architectural a été préféré à une architecture microservices, qui aurait été surdimensionnée pour l'échelle du projet et les contraintes d'hébergement de Toulouse INP.

Le système s'articule autour de cinq couches distinctes :

\begin{itemize}
    \item \textbf{La couche présentation} : responsable du rendu des interfaces
    et de la gestion des interactions utilisateur.
    \item \textbf{La couche applicative} : porte la logique métier, la validation
    et l'orchestration des domaines.
    \item \textbf{La couche asynchrone} : prend en charge les traitements longs
    découplés des requêtes, tels que l'algorithme d'affectation ou les
    synchronisations nocturnes.
    \item \textbf{La couche données} : assure la persistance relationnelle et
    le stockage des fichiers justificatifs.
    \item \textbf{La couche intégration} : gère la connexion avec les systèmes
    externes (MoveON, Pégase, Eudonet) via des adaptateurs dédiés.
\end{itemize}

La section suivante détaille l'implémentation concrète de cette architecture en couches, avec les technologies retenues pour chacune d'entre elles.

\subsection{Vue d'ensemble}

La plateforme repose sur une architecture en cinq couches qui s'appuie sur le modèle 3-tiers classique tout en l'enrichissant d'une couche asynchrone dédiée aux traitements longs. Chaque couche a une frontière bien définie : aucun composant Next.js n'accède à la base de données directement, aucune tâche asynchrone ne peut bloquer une requête HTTP.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{figures/architecture/Architecture-Logicielle.png}
  \caption{Architecture logicielle}
  \label{fig:archi-logique}
\end{figure}

La figure~\ref{fig:archi-logique} donne une vue d'ensemble du système. Les flux sont unidirectionnels et bien délimités. Le frontend Next.js 14 s'adresse exclusivement à l'API Django Ninja via des appels REST sur HTTPS — jamais directement à la base de données. Django-Q2 s'exécute dans un processus séparé et partage le même PostgreSQL que l'applicatif, ce qui lui permet de fonctionner comme broker de messages sans service externe supplémentaire. PostgreSQL et MinIO sont des services internes non accessibles depuis l'extérieur du réseau Docker. Les adaptateurs ETL sont physiquement séparés des modules métier, précisément parce qu'ils dépendent de sources externes (MoveON, Pégase, Eudonet) dont la disponibilité n'est pas garantie. L'authentification passe par le CAS OIDC de Toulouse INP : à chaque requête, le token JWT est validé et le rôle (\texttt{ADMIN\_RI} ou \texttt{ETUDIANT}) est extrait pour contrôler les accès.

\subsection{Couche présentation — Next.js 14}

La couche présentation est développée en \textbf{Next.js 14} avec \textbf{TypeScript} et \textbf{Tailwind CSS}. Elle expose deux espaces fonctionnellement distincts, séparés dès le middleware de routage.

\textbf{Espace administrateur RI :} pilotage de campagne, gestion des quotas par accord et par département, supervision des affectations avant publication, instruction des demandes de mobilités complémentaires, tableaux de bord de conformité CTI.

\textbf{Espace étudiant :} consultation du catalogue de destinations, suivi de l'état de candidature, déclaration d'expériences complémentaires, indicateur personnel de durée CTI.

Toutes les communications entre le frontend et le backend passent par l'API REST, en JSON sur HTTPS, avec un token JWT joint à chaque requête.

\subsection{Couche applicatif — Django 5 + Django Ninja}

Le backend concentre la logique métier du système. Il est découpé en modules Django autonomes, chacun responsable d'un domaine précis, selon les principes DDD décrits en début de chapitre. Cette organisation garantit qu'une modification dans le domaine de l'affectation ne peut pas affecter le comportement du domaine CTI ou des imports.

\textbf{Django Ninja} est utilisé pour exposer l’API REST. Chaque module définit ses propres schémas pour valider les données en entrée et structurer les réponses. L’authentification repose sur le middleware OIDC (CAS Toulouse INP), qui vérifie le token et associe l’utilisateur à chaque requête.

\subsection{Couche traitement asynchrone — Django-Q2}

Plutôt que de bloquer l'interface le temps qu'un calcul se termine, les traitements longs sont soumis à une file de tâches gérée par \textbf{Django-Q2}. Ce dernier utilise PostgreSQL comme broker, ce qui évite d'introduire Redis dans l'infrastructure. Deux familles de tâches y transitent :

\begin{itemize}
  \item \textbf{Tâches déclenchées par événement} : lancement de l'algorithme d'affectation, recalcul des durées CTI après chaque transition FSM, génération des rapports d'import.
  \item \textbf{Tâches planifiées (cron)} : synchronisation nocturne avec MoveON, Pégase et Eudonet ; purge des données brutes (\texttt{RawImport}) traitées depuis plus de 90 jours.
\end{itemize}

\subsection{Couche données — PostgreSQL 16}

Un seul service de données est utilisé dans l'infrastructure : \textbf{PostgreSQL 16}. Ce choix simplifie les sauvegardes et la supervision. PostgreSQL remplit ici trois fonctions différentes :

\begin{itemize}
  \item \textbf{Base de données relationnelle} : toutes les entités métier y sont stockées, avec des index composites sur \texttt{academic\_year\_id} pour les performances de filtrage par campagne.
  \item \textbf{Broker de messages Django-Q2} : la table \texttt{django\_q\_task} stocke les tâches en attente.
  % , éliminant le besoin de Redis.
  \item \textbf{Stockage des données brutes (JSONB)} : la table \texttt{RawImport} conserve les réponses JSON brutes de chaque appel API avant transformation, garantissant la possibilité de relancer les imports.
\end{itemize}

Le stockage des fichiers (justificatifs de mobilités complémentaires, templates Excel) est assuré par \textbf{MinIO}, un serveur de stockage objet compatible S3, déployé comme container Docker interne.

\subsection{Couche intégration — Adaptateurs ETL}

Chaque source externe est encapsulée dans un adaptateur dédié, isolé du reste du code métier. Quatre adaptateurs ont été développés :

\begin{itemize}
  \item \texttt{adapters/moveon.py} : extraction des accords bilatéraux, des quotas INP et des candidatures/vœux ;
  \item \texttt{adapters/pegase.py} : extraction des données académiques étudiants (INE, GPA trimestriel, département d'inscription) ;
  \item \texttt{adapters/eudonet.py} : extraction des conventions de stages à l'international ;
  \item \texttt{adapters/excel.py} : traitement des fichiers Excel standardisés (mobilités entrantes, données sans API disponible).
\end{itemize}

Tous les adaptateurs suivent le même enchaînement : récupération des données depuis la source → stockage brut en JSONB (\texttt{RawImport}) → parsing et standardisation → validation métier → persistance en base → génération du rapport d'import. En cas d'indisponibilité de la source, un mécanisme de retry exponentiel (trois tentatives) est appliqué avant qu'une alerte soit émise via \textbf{Sentry}.

\subsubsection{Stratégie d'upsert}

À la phase de persistance, chaque enregistrement est traité selon une logique d'upsert. La clé métier (généralement l'INE ou l'identifiant de l'accord) permet de déterminer si l'enregistrement est nouveau ou déjà connu. S'il est nouveau, il est inséré. S'il existe, ses champs sont comparés un à un avec la version en base : en l'absence de différence, l'enregistrement est ignoré ; si un champ a changé (par exemple un GPA révisé dans Pégase ou une date de fin de stage corrigée dans Eudonet), la mise à jour est appliquée et l'écart est consigné dans le journal d'audit. Cela permet au service RI de savoir exactement ce qui a changé d'une synchronisation à l'autre.

\subsubsection{Clé de jointure : l'INE}

L'identifiant national étudiant (INE) est la clé partagée entre
MoveON, Pégase, Eudonet et le CAS institutionnel. Toutes les données
importées sont croisées via l'INE pour construire une vue unifiée
du dossier étudiant.

Lorsque l'INE est absent d'une source (notamment Eudonet),
une stratégie de réconciliation est appliquée : matching
déterministe sur le triplet nom/prénom/date de naissance,
avec détection des cas ambigus remontés pour validation manuelle
par le service RI.

\subsection{Sécurité et contrôle d'accès}

\subsubsection{Flux d'authentification OIDC}

L'application délègue entièrement l'authentification au CAS institutionnel de Toulouse INP via OIDC. Aucun mot de passe n'est stocké côté applicatif. Le flux se déroule en quatre étapes :

\begin{enumerate}
  \item L'utilisateur accède à l'application et est redirigé vers le portail SSO institutionnel.
  \item Après authentification CAS, un token OIDC (JWT) est émis et transmis à l'application.
  \item Le backend décode le token, extrait l'INE et le groupe LDAP de l'utilisateur, et détermine automatiquement son rôle (\texttt{ADMIN\_RI} ou \texttt{ETUDIANT}).
  \item Le frontend reçoit le rôle et affiche l'espace correspondant. Les tokens ont une durée de vie courte (15 minutes) et sont renouvelés silencieusement sans interrompre la navigation.
\end{enumerate}

\subsubsection{Contrôle d'accès (RBAC)}

Les rôles sont déduits automatiquement depuis l'annuaire LDAP institutionnel, sans gestion manuelle dans l'application :

\begin{itemize}
  \item \textbf{ADMIN\_RI} : accès complet aux fonctions d'administration — imports, lancement de l'algorithme, validations, exports CTI. Toute action est enregistrée dans le journal d'audit.
  \item \textbf{ETUDIANT} : accès strictement limité à son propre dossier. Un contrôle au niveau de l'objet (\textit{object-level permission}) est appliqué sur chaque endpoint exposant des données personnelles — un étudiant ne peut pas accéder au dossier d'un autre.
\end{itemize}

\subsubsection{Gestion du renouvellement des tokens JWT}

Les tokens JWT ont une durée de vie de 15 minutes pour limiter l'exposition en cas d'interception. Côté Next.js, NextAuth gère le renouvellement silencieusement : quand le token approche de son expiration, un flux de rafraîchissement est initié via le endpoint OIDC du CAS sans interrompre la session. Côté Django, chaque requête est vérifiée par un middleware qui contrôle la signature et l'expiration du token ; un token expiré retourne un 401 et force le frontend à initier un nouveau cycle. Un token révoqué au niveau du CAS ne peut donc pas être utilisé pour accéder au backend, même si le frontend n'a pas encore détecté l'invalidation.

\subsubsection{Journal d'audit}

La traçabilité des actions administratives est assurée par \texttt{django-auditlog}, sans code supplémentaire dans les vues. Les événements enregistrés couvrent :

\begin{itemize}
  \item Authentifications réussies et tentatives échouées ;
  \item Toutes les transitions FSM (changements d'état d'une année universitaire, d'un dossier, d'une affectation) ;
  \item Modifications manuelles des affectations par le service RI (avec champ \textit{motif} obligatoire) ;
  \item Lancements d'imports ETL et résultats (source, nombre d'enregistrements traités, erreurs) ;
  \item Validations ou rejets de mobilités complémentaires ;
  \item Exports de rapports CTI.
\end{itemize}

Chaque entrée contient l'identifiant de l'auteur, l'horodatage UTC, l'entité concernée (table et clé primaire), l'action effectuée, et les valeurs avant/après modification. Le journal est stocké dans une table PostgreSQL dédiée (\texttt{auditlog\_logentry}), accessible en lecture seule. La politique de rétention est de sept ans. Aucune entrée ne peut être modifiée ou supprimée depuis l'application — toute suppression nécessite un accès direct à la base, lui-même tracé au niveau opérateur.

\subsubsection{Protection des données (RGPD)}

La plateforme traite des données personnelles étudiantes (INE, email, date de naissance, résultats académiques) soumises au RGPD. Quatre mesures techniques ont été intégrées dès la conception :

\begin{itemize}
  \item \textbf{Chiffrement au repos} : les champs sensibles sont chiffrés en base via \texttt{pgcrypto} ; leur lecture requiert la clé de déchiffrement qui n'est jamais stockée dans le code.
  \item \textbf{Chiffrement en transit} : TLS est obligatoire sur tous les endpoints ; les communications HTTP sont systématiquement redirigées vers HTTPS par Nginx.
  \item \textbf{Stockage des justificatifs} : les fichiers uploadés (justificatifs de mobilités complémentaires) sont chiffrés côté serveur dans MinIO (SSE-S3) et supprimés automatiquement après validation et expiration du délai de conservation.
  \item \textbf{Droit à l'oubli} : une procédure d'anonymisation est prévue après diplômation — les données nominatives sont effacées, les statistiques agrégées sont conservées pour les rapports CTI.
\end{itemize}

\subsection{Flux réseau}

Nginx est le seul point d'entrée du système : les requêtes vers \texttt{/api/*} sont acheminées vers \texttt{backend:8000}, toutes les autres vers \texttt{frontend:3000}. Le container \texttt{backend} dialogue avec la base de données pour les opérations métier et avec MinIO pour la gestion des fichiers. Le \texttt{worker} Django-Q2 utilise le même PostgreSQL comme file de messages — aucun Redis ni RabbitMQ n'est nécessaire. Les appels sortants vers MoveON, Pégase, Eudonet et le CAS passent uniquement par le container \texttt{backend}.

\subsection{Environnements}

Trois environnements coexistent, avec une parité de configuration maximale entre eux :

\begin{itemize}
  \item \textbf{Développement} : Docker Compose local, données anonymisées, variables d'environnement dans \texttt{.env}. Chaque développeur dispose d'un environnement reproductible en une commande.
  \item \textbf{Staging} : copie conforme de la production hébergée sur le serveur institutionnel, utilisée pour les tests d'acceptation (UAT) avec le service RI avant chaque mise en production.
  \item \textbf{Production} : déploiement final sur le serveur on-premise, avec sauvegardes PostgreSQL quotidiennes, alertes via Sentry et métriques via Prometheus/Grafana.
\end{itemize}

\subsection{CI/CD}

Le pipeline CI/CD sur \textbf{GitHub Actions} s'exécute à chaque push. Trois étapes s'enchaînent :

\begin{itemize}
  \item \textbf{Lint et tests} : le linter \texttt{ruff} vérifie la qualité du code Python, puis \texttt{pytest} exécute la suite de tests complète.
  \item \textbf{Build} : construction des images Docker et vérification que l'ensemble des services démarre sans erreur.
  \item \textbf{Déploiement staging} : déploiement automatique sur l'environnement de staging à chaque merge sur \texttt{main}, sans intervention manuelle.
\end{itemize}

\subsection{Stratégie de migration de schéma}

Les migrations Django sont appliquées automatiquement avant le démarrage du serveur applicatif, ce qui garantit que le code et le schéma de base de données sont toujours cohérents. La stratégie retenue est celle des migrations additives en deux temps : on ajoute d'abord le nouveau champ (migration non destructive), et on supprime les éléments devenus inutiles dans une migration ultérieure, une fois que le code de production n'y fait plus référence. Cette approche permet de déployer sans fenêtre de maintenance et sans risque de rupture entre le code et le schéma. Chaque fichier de migration est versionné dans le dépôt git au même titre que le code, et relu avant intégration.

\subsection{Stratégie de rollback}

Si un incident survient après un déploiement, le rollback se déroule en deux temps. L'image Docker précédente est remise en service en ciblant son tag de version. Si la migration de schéma était irréversible (suppression de colonne par exemple), une restauration depuis la sauvegarde pré-déploiement est effectuée — c'est pourquoi une sauvegarde complète est systématiquement déclenchée juste avant tout déploiement en production. Pour les migrations réversibles, un retour en arrière via la commande Django est possible sans restauration complète.

\subsection{Politique de sauvegarde}

Deux niveaux de sauvegarde sont mis en place. Des sauvegardes logiques PostgreSQL sont générées chaque nuit et conservées 30 jours sur un volume distinct du volume de données. Des sauvegardes physiques hebdomadaires couvrent l'intégralité des données et sont archivées pendant six mois, permettant une restauration fine en combinaison avec les journaux transactionnels.

Un test de restauration est effectué chaque mois sur l'environnement staging : on restaure la sauvegarde la plus récente et on vérifie l'intégrité des données via un script de contrôle (comptages par table, contraintes référentielles). Cette procédure mesure le \textit{Recovery Time Objective} réel et permet de détecter un problème avant qu'il ne se révèle en production.

\subsection{Gestion des secrets}

Aucun secret n'est présent dans le dépôt git. Les variables sensibles — \texttt{SECRET\_KEY}, mots de passe PostgreSQL, clés d'API MoveON, Pégase, Eudonet, tokens MinIO — sont injectées au runtime via un fichier \texttt{.env.prod} stocké uniquement sur le serveur de production. Le \texttt{.gitignore} exclut tous les fichiers \texttt{.env.*}, à l'exception d'un fichier de référence avec des valeurs fictives fourni pour le développement local.

\subsection{Principes structurants}

Trois décisions de conception traversent l'ensemble du modèle et méritent d'être explicitées.

\subsubsection{L'année universitaire comme axe temporel}
Toutes les entités opérationnelles — dossiers, vœux, affectations, mobilités, imports — sont rattachées à une \texttt{AcademicYear}. Cette clé de partitionnement logique garantit deux propriétés : l'historique des campagnes passées est complet et consultable, et dès qu'une année est clôturée, ses données basculent automatiquement en lecture seule.

\subsubsection{L'INE comme identifiant pivot}
L'identifiant national étudiant (INE) est le seul identifiant commun à toutes les sources — MoveON, Pégase, Eudonet et le CAS OIDC. Tous les imports sont croisés via l'INE pour construire une vue unifiée du dossier étudiant. Quand un enregistrement arrive sans INE valide (cas courant dans Eudonet), une réconciliation déterministe sur le triplet nom / prénom / date de naissance est appliquée, et les cas ambigus sont remontés pour validation manuelle par le service RI.

\subsubsection{Hiérarchie quotas INP / quotas N7}
MoveON ne connaît les quotas qu'à l'échelle de l'INP. Pour gérer la répartition interne à l'ENSEEIHT, le modèle introduit quatre niveaux : le quota INP importé depuis MoveON, l'estimation N7 calculée par l'administrateur, un éventuel ajustement manuel, et la répartition finale par département pédagogique. Ce découpage assure à la fois la conformité avec MoveON et la granularité nécessaire à l'algorithme d'affectation.

\section{Machines à états finis (FSM)}
% ─────────────────────────────────────────────────────────────

\subsection{Principe et implémentation}

Dans un système comme celui-ci, certaines entités ne peuvent pas changer d'état librement. Une campagne clôturée ne doit pas pouvoir être rouverte, une affectation validée ne doit pas être modifiable sans trace, et l'algorithme ne doit pas s'exécuter sur des données incomplètes. Ces contraintes sont encodées dans des machines à états finis, implémentées via \texttt{django-fsm}. Le champ de statut est déclaré avec l'option \texttt{protected=True} : toute tentative de modification directe du statut — sans passer par une méthode de transition nommée — lève immédiatement une exception. Il n'est donc pas possible de contourner ces règles, même par une opération en base de données effectuée manuellement.

Chaque transition marque un cap dans le déroulement de la campagne.

\begin{itemize}
  \item \textbf{initialization} → \textbf{recommendation} (\texttt{open\_recommendation}) : les étudiants peuvent désormais consulter le catalogue de destinations et formuler leurs vœux.
  \item \textbf{recommendation} → \textbf{consolidation} (\texttt{start\_consolidation}) : la fenêtre de saisie des vœux se ferme, le GPA est gelé à la date du jour, et la synchronisation finale avec MoveON est déclenchée.
  \item \textbf{consolidation} → \textbf{pre\_assignment} (\texttt{launch\_pre\_assignment}) : l'algorithme Gale-Shapley est soumis à Django-Q2 pour exécution asynchrone.
  \item \textbf{pre\_assignment} → \textbf{validation} (\texttt{submit\_for\_validation}) : les propositions d'affectation sont soumises à l'examen du service RI, qui peut les ajuster avant publication.
  \item \textbf{validation} → \textbf{closed} (\texttt{close}) : les résultats sont publiés et toutes les données de la campagne passent en lecture seule.
\end{itemize}

Chaque transition est réservée aux utilisateurs \texttt{ADMIN\_RI}. Le tableau ci-dessous liste les conditions que le système vérifie avant d'autoriser chaque passage d'état, ainsi que le comportement en cas d'échec.

\section{Flux de données : de la source au workflow}
% ─────────────────────────────────────────────────────────────

Chaque information importée dans le système suit un même parcours balisé, du fichier brut jusqu’à son intégration dans les entités métier. Ce parcours est délibérément découpé pour garantir qu’aucune donnée non validée ne peut déclencher un workflow, et que chaque étape est indépendamment traçable et rejouable.

\begin{enumerate}
  \item \textbf{Récupération :} la tâche Django-Q2 interroge la source (API MoveON, Pégase, Eudonet ou fichier Excel). La réponse brute est immédiatement sérialisée en JSONB dans \texttt{RawImport}. Aucune transformation n’a encore eu lieu à ce stade — ce qui signifie que si un traitement ultérieur échoue, l’import peut être rejoué sans rappeler la source.
  \item \textbf{Nettoyage et validation :} un pipeline Python normalise les chaînes, croise les INE, détecte les doublons et vérifie les règles métier. Les enregistrements qui ne passent pas la validation sont consignés dans le rapport d’import avec le motif de rejet, sans interrompre le reste du traitement.
  \item \textbf{Persistance :} les enregistrements validés sont intégrés en base par upsert atomique, rattachés à l’année universitaire en cours.
  \item \textbf{Déclenchement des workflows :} chaque entité créée entre dans l’état initial de sa FSM. Un vœu importé commence en statut \texttt{candidate} ; une affectation créée par l’algorithme commence en \texttt{proposed}. Toute progression ultérieure passe obligatoirement par une transition FSM explicite.
  \item \textbf{Supervision :} l’administrateur consulte le rapport d’import, traite les anomalies signalées et confirme le passage à la phase suivante de la campagne.
\end{enumerate}

\subsection{Détail de l’étape de nettoyage et validation}

L’étape de nettoyage et validation est la plus délicate du pipeline : c’est là que les données brutes issues de sources hétérogènes deviennent exploitables par le système métier. Elle s’intercale entre la phase de récupération (stockage JSONB) et la persistance en base.
\subsubsection{Description du processus de transformation}

Les données importées arrivent sous des formats incompatibles : une API REST renvoie du JSON, Eudonet exporte du XML, les fichiers Excel du service RI utilisent des colonnes nommées différemment selon l’agent qui les a créés. Le pipeline de transformation commence donc par convertir toutes ces entrées dans une représentation intermédiaire commune, avant d’appliquer les mêmes règles de nettoyage quel que soit l’origine. Cette approche modulaire permet d’ajouter une nouvelle source sans modifier la logique de validation.

\paragraph{Standardisation des formats}
\begin{itemize}
    \item Normalisation des chaînes de caractères : suppression des espaces en début/fin, homogénéisation de la casse pour les codes (INE, codes ISO pays).
    
    \item \textbf{Gestion des accents :}
    \begin{itemize}
        \item Les accents sont conservés pour les champs descriptifs (noms propres, universités, pays) afin de préserver l’intégrité sémantique des données.
        
        \item Lors des opérations de recherche, de comparaison ou de détection de similarité (\textit{matching}), les comparaisons sont effectuées de manière insensible aux accents afin d’éviter les divergences liées aux variations d’écriture.
    \end{itemize}
    
    \item Uniformisation des formats de dates (ISO 8601).
    
    \item Conversion des types (ex : chaînes vers entiers pour les identifiants).
\end{itemize}

\paragraph{Normalisation sémantique}
\begin{itemize}
    \item Harmonisation des noms d’universités via une table de correspondance (\textit{lookup table}) :
    \begin{itemize}
        \item Les données sources peuvent contenir différentes variantes pour une même université (abréviations, différences de langue, fautes de frappe).
        
        \item Une table de correspondance permet d’associer ces variantes à une valeur unique de référence.
        
        \item Cette approche garantit la cohérence des données et évite les duplications logiques lors des traitements.
    \end{itemize}
    
    \item Normalisation des pays selon un référentiel standard (ISO 3166).
    
    \item Mapping des valeurs hétérogènes vers des valeurs métier uniques (ex : “FR”, “France”, “france” $\rightarrow$ “France”).
\end{itemize}

\paragraph{Gestion des valeurs manquantes}
\begin{itemize}
    \item Identification des champs obligatoires (INE, université, type de mobilité).
    
    \item Si une valeur obligatoire est manquante, l’enregistrement est rejeté et consigné dans le rapport d’import avec la raison de l’erreur.
    
    \item Si les champs manquants ne sont pas critiques, l’enregistrement est conservé et peut être sauvegardé en base de données.
\end{itemize}

\paragraph{Détection et gestion des doublons}
\begin{itemize}
    \item Les doublons sont identifiés à partir d’une clé composite construite à partir de plusieurs attributs pertinents (par exemple : INE, entité concernée, période), permettant de représenter de manière unique un enregistrement métier.

    \item La composition de cette clé peut varier selon le type de donnée traité (étudiant, souhait, accord, etc.), afin de s’adapter aux spécificités de chaque entité.

    \item Chaque enregistrement est comparé aux données existantes afin de détecter les occurrences identiques.

    \item En cas de doublon exact, l’enregistrement est ignoré afin d’éviter la duplication des données.

    \item Les cas détectés sont tracés dans le rapport d’import pour assurer la traçabilité.
\end{itemize}

\paragraph{Validation métier}
\begin{itemize}
    \item Vérification de la cohérence avec les données Pégase (existence de l’étudiant via INE).
    
    \item Contrôle des règles métier (nombre maximum de vœux, compatibilité des destinations).
\end{itemize}

\paragraph{Traçabilité et gestion des erreurs}
\begin{itemize}
    \item Journalisation des erreurs dans un rapport d’import structuré.
    
    \item Stockage des données rejetées avec leur motif (audit et reprise).
    
    \item Attribution d’un identifiant de traitement pour chaque batch.
\end{itemize}

\subsubsection{Architecture du pipeline de nettoyage}

Le pipeline de nettoyage est conçu comme un module autonome intégré dans le flux global. Il fonctionne par batch afin d’assurer l’isolation des traitements et la robustesse du système.

\begin{itemize}
    \item \textbf{Entrée :} données JSON issues du pipeline global.
    \item \textbf{Parsing :} transformation en objets manipulables.
    \item \textbf{Nettoyage :} standardisation et normalisation.
    \item \textbf{Validation :} application des règles métier.
    \item \textbf{Sortie :}
    \begin{itemize}
        \item Données valides → persistance.
        \item Données invalides → rapport d’erreurs.
    \end{itemize}
\end{itemize}

\medskip

Cette architecture garantit :
\begin{itemize}
    \item une \textbf{traçabilité complète} grâce au stockage JSONB,
    \item une \textbf{robustesse} via le traitement isolé de chaque enregistrement,
    \item une \textbf{reprise sur erreur} par batch,
    \item une \textbf{maintenabilité} grâce à la modularité du pipeline.
\end{itemize}

\subsubsection{Technologies et outils utilisés}
\begin{itemize}
    \item \textbf{Python} : traitement et transformation des données.
    \item \textbf{Pandas} : manipulation et nettoyage des datasets.
    \item \textbf{Regex} : validation et transformation des formats.
    \item \textbf{PostgreSQL (JSONB)} : stockage temporaire des données brutes.
\end{itemize}

\medskip
Ce pipeline garantit qu'aucune donnée non validée n'atteint la couche métier. Chaque rejet est documenté dans le rapport d'import avec le motif exact, ce qui permet à l'administrateur de corriger la source ou de saisir manuellement les données manquantes.
