\subsection{Priorités MoSCoW}

Chaque user story est priorisée selon la méthode MoSCoW :

\begin{itemize}[label=•]
    \item M pour "Must Have" (Doit avoir) : Il s'agit des fonctionnalités qui sont absolument essentielles au succès du projet. Si ces fonctionnalités ne sont pas livrées, le projet est considéré comme un échec.
    \item S pour "Should Have" (Devrait avoir) : Il s'agit des fonctionnalités qui sont importantes mais pas vitales pour le succès du projet. Si possible, elles devraient être livrées, mais il est acceptable de les reporter à une version ultérieure si nécessaire.
    \item C pour "Could Have" (Pourrait avoir) : Il s'agit des fonctionnalités qui sont souhaitables mais pas essentielles pour le succès du projet. Elles ne sont intégrées à un sprint que si la capacité restante le permet, après réalisation et validation des fonctionnalités MVP prévues dans les sprints prioritaires.
    \item W pour "Won't Have" (N'aura pas) : Il s'agit des fonctionnalités qui ne seront pas livrées dans cette version du projet, mais qui peuvent être considérées pour une version ultérieure.
\end{itemize}

\section{Architecture logicielle}
% ─────────────────────────────────────────────────────────────

\subsection{Vue d'ensemble}

L'architecture suit un modèle \textbf{3-tiers} classique, enrichi d'une couche de traitement asynchrone. Les trois niveaux sont clairement séparés : présentation (Next.js), applicatif (Django + Django Ninja) et données (PostgreSQL). Les traitements lourds sont délégués à une couche asynchrone indépendante (Django-Q2).

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{figures/architecture/Architecture-Logicielle.png}
  \caption{Architecture logicielle}
  \label{fig:archi-logique}
\end{figure}

La figure \ref{fig:archi-logique} représente l'architecture logicielle du système selon un modèle en cinq couches. La couche \textbf{Présentation} (Next.js 14) communique avec la couche \textbf{Applicative} (Django 5 + Django Ninja) exclusivement via des appels REST/JSON sur HTTPS ; aucun composant Next.js n'accède directement à la base de données. La couche \textbf{Asynchrone} (Django-Q2) partage la même base de données que la couche applicative — PostgreSQL joue ici le rôle de broker de messages — et s'exécute dans un processus distinct pour ne pas bloquer les requêtes HTTP. La couche \textbf{Données} regroupe PostgreSQL pour la persistance relationnelle et JSONB, et MinIO pour les fichiers binaires ; ces deux services sont internes et non accessibles directement depuis l'extérieur. La couche \textbf{Intégration} rassemble les adaptateurs ETL : elle est positionnée à part des couches métier car elle dépend de systèmes externes (MoveON, Pégase, Eudonet) dont la disponibilité n'est pas garantie. L'authentification suit un flux OIDC : l'utilisateur est redirigé vers le CAS de Toulouse INP, qui renvoie un token JWT ; la couche applicative valide ce token à chaque requête et en extrait le rôle (\texttt{ADMIN\_RI} ou \texttt{ETUDIANT}).

\subsection{Couche présentation — Next.js 14}

Le frontend est développé avec \textbf{Next.js 14}, \textbf{TypeScript} et \textbf{Tailwind CSS}. Il expose deux espaces distincts selon le rôle de l'utilisateur authentifié.

\textbf{Espace administrateur RI :} console de supervision de campagne, gestion des quotas, supervision des affectations, instruction des mobilités complémentaires, tableaux de bord CTI.

\textbf{Espace étudiant :} catalogue des destinations, suivi de candidature, déclaration d'expériences complémentaires, indicateur CTI.

Le frontend communique exclusivement avec le backend via l'API REST au format JSON, avec authentification par token JWT.

\subsection{Couche traitement asynchrone — Django-Q2}

Les traitements qui ne doivent pas bloquer l'interface sont délégués à \textbf{Django-Q2}, qui utilise PostgreSQL directement comme broker de messages. Deux catégories de tâches sont gérées :

\begin{itemize}
  \item \textbf{Tâches déclenchées par événement} : lancement de l'algorithme d'affectation, recalcul des durées CTI après chaque transition FSM, génération des rapports d'import.
  \item \textbf{Tâches planifiées (cron)} : synchronisation nocturne avec MoveON, Pégase et Eudonet ; purge des données brutes (\texttt{RawImport}) traitées depuis plus de 90 jours.
\end{itemize}

\subsection{Couche données — PostgreSQL 16}

\textbf{PostgreSQL 16} est le seul système de persistance du projet. Il joue trois rôles distincts :

\begin{itemize}
  \item \textbf{Base de données relationnelle} : toutes les entités métier y sont stockées, avec des index composites sur \texttt{academic\_year\_id} pour les performances de filtrage par campagne.
  \item \textbf{Broker de messages Django-Q2} : la table \texttt{django\_q\_task} stocke les tâches en attente.
  % , éliminant le besoin de Redis.
  \item \textbf{Stockage des données brutes (JSONB)} : la table \texttt{RawImport} conserve les réponses JSON brutes de chaque appel API avant transformation, garantissant la possibilité de relancer les imports.
\end{itemize}

Le stockage des fichiers (justificatifs de mobilités complémentaires, templates Excel) est assuré par \textbf{MinIO}, un serveur de stockage objet compatible S3, déployé comme container Docker interne.

\subsection{Couche intégration — Adaptateurs ETL}

Chaque source externe dispose d'un module adaptateur isolé :

\begin{itemize}
  \item \texttt{adapters/moveon.py} : extraction des accords, quotas et vœux ;
  \item \texttt{adapters/pegase.py} : extraction des données académiques (INE, GPA, département) ;
  \item \texttt{adapters/eudonet.py} : extraction des conventions de stages internationaux ;
  \item \texttt{adapters/excel.py} : parsing des templates Excel standardisés (mobilités entrantes, fallbacks).
\end{itemize}

Chaque adaptateur suit le pipeline ETL suivant : récupération → stockage brut (JSONB) → parsing → standardisation → validation métier → persistance → rapport d'import.

En cas d'échec API, un mécanisme de retry exponentiel (3 tentatives) est appliqué avant de déclencher une alerte via \textbf{Sentry}.

\subsubsection{Stratégie d'upsert}

Lors de la phase de persistance, chaque enregistrement issu du pipeline est traité selon une logique d'upsert : si un enregistrement correspondant n'existe pas encore en base, il est inséré ; s'il existe déjà (identifié par la clé métier, en général l'INE ou l'identifiant de l'accord), il est comparé champ par champ à la version en base. Si les valeurs sont identiques, l'enregistrement est ignoré. Si des différences sont détectées, la mise à jour est appliquée et la modification est tracée dans le journal d'audit — ce qui permet au service RI de savoir précisément quelles données ont changé d'une synchronisation à l'autre (par exemple, un GPA révisé dans Pégase ou une date de fin de stage corrigée dans Eudonet).

\subsubsection{Clé de jointure : l'INE}

L'identifiant national étudiant (INE) est la clé partagée entre
MoveON, Pégase, Eudonet et le CAS institutionnel. Toutes les données
importées sont croisées via l'INE pour construire une vue unifiée
du dossier étudiant.

Lorsque l'INE est absent d'une source (notamment Eudonet),
une stratégie de réconciliation est appliquée : matching
déterministe sur le triplet nom/prénom/date de naissance,
avec détection des cas ambigus remontés pour validation manuelle
par le service RI.

\subsection{Sécurité et contrôle d'accès}

\subsubsection{Flux d'authentification OIDC}

L'authentification est assurée par le CAS institutionnel de
Toulouse INP via le protocole OIDC. Le flux se déroule en
quatre étapes :

\begin{enumerate}
  \item L'utilisateur accède à l'application et est redirigé
        vers le portail SSO institutionnel.
  \item Après authentification CAS réussie, un token OIDC (JWT)
        est émis et transmis à l'application.
  \item Le backend décode le token, récupère l'INE et le groupe
        LDAP de l'utilisateur, et détermine automatiquement son
        rôle (\texttt{ADMIN\_RI} ou \texttt{ETUDIANT}).
  \item Le frontend reçoit le rôle et affiche l'espace correspondant.
        Les tokens JWT ont une durée de vie courte (15 minutes),
        avec un mécanisme de renouvellement géré côté serveur.
\end{enumerate}

\subsubsection{Contrôle d'accès (RBAC)}

Deux rôles sont définis et détectés automatiquement depuis
l'annuaire institutionnel :

\begin{itemize}
  \item \textbf{ADMIN\_RI} : accès complet aux fonctionnalités
        d'administration — imports, algorithme, validations,
        exports CTI. Toute action est tracée dans l'AuditLog.
  \item \textbf{ETUDIANT} : accès restreint à son propre dossier
        uniquement. Un contrôle de type \textit{object-level
        permission} est appliqué sur chaque endpoint exposant
        des données personnelles.
\end{itemize}

\subsubsection{Gestion du renouvellement des tokens JWT}

Le token JWT émis par le CAS de Toulouse INP a une durée de vie courte (15 minutes) pour limiter le risque en cas d'interception. Côté Next.js, NextAuth gère automatiquement le renouvellement : lorsque le token approche de son expiration, NextAuth initie silencieusement un flux de rafraîchissement via le endpoint OIDC du CAS sans interrompre la navigation de l'utilisateur. Côté backend Django, chaque requête API passe par un middleware qui vérifie la signature et l'expiration du token ; si le token est expiré, la requête est rejetée avec un code 401 et le frontend déclenche un nouveau cycle d'authentification. Cette architecture garantit qu'un token révoqué au niveau du CAS ne peut plus être utilisé pour accéder au backend, même si le frontend n'a pas encore détecté l'expiration.

\subsubsection{Journal d'audit}

Le journal d'audit est géré par \texttt{django-auditlog}, configuré pour enregistrer automatiquement les événements suivants :

\begin{itemize}
  \item Authentifications réussies et tentatives échouées ;
  \item Toutes les transitions FSM (changements d'état d'une année universitaire, d'un dossier, d'une affectation) ;
  \item Modifications manuelles des affectations par le service RI (avec champ \textit{motif} obligatoire) ;
  \item Lancements d'imports ETL et résultats (source, nombre d'enregistrements traités, erreurs) ;
  \item Validations ou rejets de mobilités complémentaires ;
  \item Exports de rapports CTI.
\end{itemize}

Chaque entrée enregistre l'identifiant de l'utilisateur auteur de l'action, l'horodatage UTC, l'entité concernée (table + clé primaire), l'action réalisée et les valeurs avant/après modification. Le journal est stocké dans une table PostgreSQL dédiée (\texttt{auditlog\_logentry}), accessible en lecture seule depuis l'interface d'administration Django.

La politique de rétention est de 7 ans, alignée sur les exigences de traçabilité. La consultation est possible depuis l'interface d'administration Django (filtres par utilisateur, par entité, par période) ou via un endpoint API réservé au rôle \texttt{ADMIN\_RI}. Aucune entrée d'audit ne peut être modifiée ou supprimée depuis l'application — les suppressions éventuelles nécessitent un accès direct à la base de données avec une traçabilité opérateur.

\subsubsection{Protection des données (RGPD)}

\begin{itemize}
  \item \textbf{Chiffrement au repos} : les champs sensibles
        (INE, email, date de naissance) sont chiffrés en base
        via \texttt{pgcrypto}.
  \item \textbf{Chiffrement en transit} : TLS obligatoire sur
        tous les endpoints.
  \item \textbf{Stockage des justificatifs} : fichiers chiffrés
        (SSE-S3) dans MinIO, supprimés automatiquement après
        validation et expiration du délai de conservation.
  \item \textbf{Droit à l'oubli} : procédure d'anonymisation
        des données personnelles après diplômation, tout en
        conservant les statistiques agrégées pour les rapports CTI.
\end{itemize}

\subsection{Flux réseau}

Les requêtes entrantes arrivent sur \textbf{Nginx}. Nginx route vers :
\begin{itemize}
  \item le container \texttt{frontend} pour les pages et ressources statiques Next.js ;
  \item le container \texttt{backend} pour les appels à l'API REST (\texttt{/api/*}).
\end{itemize}

Le container \texttt{backend} communique avec \texttt{db} pour toutes les opérations de données, et avec \texttt{minio} pour le stockage de fichiers. Le container \texttt{worker} partage la même base de données que \texttt{backend} — c'est ainsi que Django-Q2 utilise PostgreSQL comme broker sans service supplémentaire. Les APIs externes (MoveON, Pégase, Eudonet, CAS) sont accessibles depuis le serveur via HTTPS sortant.

\subsection{Environnements}

Trois environnements sont maintenus :

\begin{itemize}
  \item \textbf{Développement} : Docker Compose local avec des jeux de données anonymisés. Les variables d'environnement sont chargées depuis un fichier \texttt{.env}.
  \item \textbf{Staging} : reproduction fidèle de la production sur le serveur institutionnel, utilisée pour les tests d'acceptation (UAT) avec le service RI avant chaque mise en production.
  \item \textbf{Production} : déploiement final sur le serveur on-premise, avec sauvegardes PostgreSQL quotidiennes et supervision via \textbf{Sentry} (erreurs applicatives) et \textbf{Prometheus/Grafana} (métriques système).
\end{itemize}

\subsection{CI/CD}

Un pipeline CI/CD est mis en place sur \textbf{GitHub Actions} avec trois étapes automatisées à chaque push :
\begin{itemize}
  \item \textbf{Lint + tests unitaires} : exécution de la suite de tests Python (pytest) et du linter (ruff) ;
  \item \textbf{Build} : construction des images Docker ;
  \item \textbf{Déploiement automatique} sur staging à chaque merge sur la branche \texttt{main}.
\end{itemize}

\subsection{Stratégie de migration de schéma}

Django gère les évolutions du schéma de base de données via son système de migrations intégré. À chaque déploiement, les migrations sont appliquées avant le démarrage du serveur applicatif afin de garantir la cohérence entre le code exécuté et la structure de la base de données.

La stratégie retenue favorise les migrations additives en deux temps : on commence par ajouter le nouveau champ ou la nouvelle table (migration non destructive), puis on supprime les éléments obsolètes dans une migration ultérieure une fois que le code de production ne les référence plus. Cette approche évite les ruptures entre le code et le schéma lors d'un déploiement sans fenêtre de maintenance.

Les migrations Django sont versionnées dans le dépôt git, au même titre que le code. Toute modification du modèle donne lieu à un fichier de migration dédié, relu avant intégration afin de vérifier qu'il respecte la stratégie de déploiement retenue.

\subsection{Stratégie de rollback}

En cas d'incident après un déploiement, le rollback se déroule en deux étapes. D'abord, l'image Docker précédente est remise en service via Docker Compose en pointant vers le tag de la version antérieure. Ensuite, si la migration de schéma était irréversible (ex. : suppression de colonne), une restauration à partir de la sauvegarde pré-déploiement est effectuée. Pour cette raison, une sauvegarde complète de la base de données est systématiquement déclenchée avant chaque déploiement en production.

Lorsque les migrations sont réversibles, le retour à une version antérieure du schéma peut être réalisé sans restauration complète. L'état des migrations est contrôlé avant toute opération afin d'identifier précisément la version cible et d'éviter les incohérences entre l'application et la base de données.

\subsection{Politique de sauvegarde}

Deux niveaux de sauvegarde coexistent.

\textbf{Sauvegardes logiques quotidiennes} : une sauvegarde logique de la base est générée chaque nuit dans un format restaurable PostgreSQL. Ces sauvegardes sont conservées pendant 30 jours et stockées sur un volume séparé du serveur, distinct du volume de données PostgreSQL.

\textbf{Sauvegardes physiques hebdomadaires} : une copie complète des données PostgreSQL est réalisée chaque semaine. Elle permet une restauration plus fine en combinaison avec les journaux transactionnels archivés. Ces sauvegardes sont conservées pendant 6 mois.

Un test de restauration est effectué manuellement une fois par mois sur l'environnement staging : la procédure consiste à restaurer la sauvegarde la plus récente et à vérifier l'intégrité des données via un script de contrôle qui vérifie les comptages par table et les contraintes référentielles. Ce test documente le \textit{Recovery Time Objective} (RTO) réel et détecte d'éventuels problèmes avant qu'ils ne surviennent en production.

\subsection{Gestion des secrets}

Aucun secret n'est présent dans le dépôt git. Les variables sensibles — \texttt{SECRET\_KEY} Django, mots de passe PostgreSQL, clés d'API MoveON/Pégase/Eudonet, tokens MinIO — sont injectées au runtime via des variables d'environnement déclarées dans un fichier \texttt{.env.prod} hébergé uniquement sur le serveur de production, et jamais versionné. Le fichier \texttt{.gitignore} exclut explicitement tous les fichiers \texttt{.env.*} à l'exception du fichier de développement avec des valeurs fictives.

En développement local, un fichier de configuration contenant uniquement des valeurs fictives ou non sensibles est fourni à titre de référence. La séparation claire entre les environnements garantit qu'aucune valeur de production ne peut se retrouver accidentellement dans le code source.

\subsection{Principes structurants}

\subsubsection{L'année universitaire comme axe temporel.}
Toutes les entités opérationnelles (dossiers, vœux, affectations,
mobilités, imports) sont rattachées à une \texttt{AcademicYear}.
Ce rattachement garantit l'historisation complète des campagnes
passées et le basculement automatique en lecture seule dès la
clôture d'une année.

\subsubsection{L'INE comme clé de jointure universelle.}
L'identifiant national étudiant (INE) est la clé partagée entre
toutes les sources externes — MoveON, Pégase, Eudonet et le CAS

(cas fréquent dans Eudonet), une stratégie de réconciliation
déterministe est appliquée sur le triplet nom / prénom /
date de naissance, avec remontée manuelle des cas ambigus.

\subsubsection{Séparation quotas INP / quotas N7.}
Les accords MoveON sont définis à l'échelle de l'INP global.
Le modèle intègre une hiérarchie de quotas à quatre niveaux —
quota INP importé, estimation N7 calculée, ajustement manuel
de l'administrateur, et répartition par département N7 —
afin de respecter les contraintes institutionnelles tout en
offrant la granularité nécessaire à l'algorithme d'affectation.

% ─────────────────────────────────────────────────────────────
\section{Machines à états finis (FSM)}
% ─────────────────────────────────────────────────────────────

\subsection{Principe et implémentation}

Plusieurs entités du système voient leur cycle de vie contrôlé par une machine à états finis, implémentée via \texttt{django-fsm}. Le champ de statut est déclaré avec l'option \texttt{protected=True} : toute tentative de modifier l'état directement — sans passer par une méthode de transition explicite — lève une exception. C'est le mécanisme qui garantit qu'une campagne clôturée ne peut pas être rouverte, qu'une affectation validée ne peut pas être modifiée silencieusement, et qu'aucune donnée non validée ne peut déclencher un workflow métier.

\section{Flux de données : de la source au workflow}
% ─────────────────────────────────────────────────────────────

Le flux de données décrit le parcours d’une information depuis son import depuis MoveON jusqu’à son intégration dans les entités métier et les machines à états du système. Ce processus garantit une séparation claire entre la couche \textit{transport} (récupération et préparation des données) et la couche \textit{métier} (validation, persistance et déclenchement des workflows).

\begin{enumerate}
  \item \textbf{Récupération (Transport) :} la tâche Django-Q2 interroge l'API MoveON via OAuth2 et récupère les vœux au format JSON. La réponse brute est stockée temporairement en JSONB dans PostgreSQL, garantissant la traçabilité et la reprise sur erreur.
  \item \textbf{Nettoyage et validation (Python) :} un pipeline de transformation vérifie les formats, détecte les doublons et croise les INE avec la base Pégase. Les enregistrements invalides sont tracés dans un rapport d'import avec la raison du rejet.
  \item \textbf{Persistance (PostgreSQL) :} les données validées sont insérées dans les tables métier (\texttt{SouhaitSejour}, \texttt{Accord}, etc.) et rattachées à l'année universitaire courante.
  \item \textbf{Activation du workflow (FSM) :} chaque enregistrement créé déclenche la machine à états correspondante. Par exemple, un \texttt{SouhaitSejour} importé est initialisé au statut \textit{Candidat}, et ne peut progresser vers \textit{Affecté} que via les transitions autorisées.
  \item \textbf{Supervision (Interface admin) :} l'administrateur consulte les résultats de l'import, résout les anomalies signalées et confirme le passage à la phase suivante de la campagne.
\end{enumerate}

\noindent Ce découpage garantit qu'aucune donnée non validée ne peut déclencher un workflow métier, et que chaque étape est auditable de manière indépendante.

\subsection{Détail de l’étape de nettoyage et validation}

Dans le flux global de traitement des données, l’étape de \textbf{nettoyage et validation} constitue un sous-processus central garantissant la qualité et la cohérence des informations avant leur intégration dans le système métier.

Cette étape s’inscrit directement après la phase de récupération et de structuration des données (JSON/JSONB), et avant leur persistance en base de données.

Afin de clarifier son fonctionnement interne, nous détaillons ci-dessous le pipeline de traitement appliqué à cette phase.
\subsubsection{Description du processus de transformation}

Le nettoyage des données constitue une étape critique du système, garantissant la qualité, la cohérence et l’exploitabilité des informations avant leur intégration métier. Les données sont issues de plusieurs sources hétérogènes (MoveON, Pégase, Eudonet, ainsi que des fichiers Excel), nécessitant un processus de nettoyage et d’harmonisation. Ce pipeline suit une approche modulaire et déterministe, inspirée des principes ETL (\textit{Extract - Transform - Load}).

\paragraph{Gestion des sources multiples}
\begin{itemize}
    \item Les données proviennent de sources hétérogènes présentant des structures et formats différents (API REST, bases de données, fichiers Excel).
    
    \item Une étape de transformation initiale permet de convertir ces données dans un format intermédiaire commun (JSON), facilitant leur traitement uniforme dans le pipeline.
    
    \item Cette homogénéisation permet d’appliquer les mêmes règles de nettoyage, de validation et de contrôle indépendamment de la source d’origine.
\end{itemize}

\paragraph{Standardisation des formats}
\begin{itemize}
    \item Normalisation des chaînes de caractères (suppression des espaces superflus, homogénéisation de la casse).
    
    \item \textbf{Gestion des accents :}
    \begin{itemize}
        \item Les accents sont conservés pour les champs descriptifs (noms propres, universités, pays) afin de préserver l’intégrité sémantique des données.
        
        \item Lors des opérations de recherche, de comparaison ou de détection de similarité (\textit{matching}), les comparaisons sont effectuées de manière insensible aux accents afin d’éviter les divergences liées aux variations d’écriture.
    \end{itemize}
    
    \item Uniformisation des formats de dates (ISO 8601).
    
    \item Conversion des types (ex : chaînes vers entiers pour les identifiants).
\end{itemize}

\paragraph{Normalisation sémantique}
\begin{itemize}
    \item Harmonisation des noms d’universités via une table de correspondance (\textit{lookup table}) :
    \begin{itemize}
        \item Les données sources peuvent contenir différentes variantes pour une même université (abréviations, différences de langue, fautes de frappe).
        
        \item Une table de correspondance permet d’associer ces variantes à une valeur unique de référence.
        
        \item Cette approche garantit la cohérence des données et évite les duplications logiques lors des traitements.
    \end{itemize}
    
    \item Normalisation des pays selon un référentiel standard (ISO 3166).
    
    \item Mapping des valeurs hétérogènes vers des valeurs métier uniques (ex : “FR”, “France”, “france” $\rightarrow$ “France”).
\end{itemize}

\paragraph{Gestion des valeurs manquantes}
\begin{itemize}
    \item Identification des champs obligatoires (INE, université, type de mobilité).
    
    \item Si une valeur obligatoire est manquante, l’enregistrement est rejeté et consigné dans le rapport d’import avec la raison de l’erreur.
    
    \item Si les champs manquants ne sont pas critiques, l’enregistrement est conservé et peut être sauvegardé en base de données.
\end{itemize}

\paragraph{Détection et gestion des doublons}
\begin{itemize}
    \item Les doublons sont identifiés à partir d’une clé composite construite à partir de plusieurs attributs pertinents (par exemple : INE, entité concernée, période), permettant de représenter de manière unique un enregistrement métier.

    \item La composition de cette clé peut varier selon le type de donnée traité (étudiant, souhait, accord, etc.), afin de s’adapter aux spécificités de chaque entité.

    \item Chaque enregistrement est comparé aux données existantes afin de détecter les occurrences identiques.

    \item En cas de doublon exact, l’enregistrement est ignoré afin d’éviter la duplication des données.

    \item Les cas détectés sont tracés dans le rapport d’import pour assurer la traçabilité.
\end{itemize}

\paragraph{Validation métier}
\begin{itemize}
    \item Vérification de la cohérence avec les données Pégase (existence de l’étudiant via INE).
    
    \item Contrôle des règles métier (nombre maximum de vœux, compatibilité des destinations).
\end{itemize}

\paragraph{Traçabilité et gestion des erreurs}
\begin{itemize}
    \item Journalisation des erreurs dans un rapport d’import structuré.
    
    \item Stockage des données rejetées avec leur motif (audit et reprise).
    
    \item Attribution d’un identifiant de traitement pour chaque batch.
\end{itemize}

\subsubsection{Architecture du pipeline de nettoyage}

Le pipeline de nettoyage est conçu comme un module autonome intégré dans le flux global. Il fonctionne par batch afin d’assurer l’isolation des traitements et la robustesse du système.

\begin{itemize}
    \item \textbf{Entrée :} données JSON issues du pipeline global.
    \item \textbf{Parsing :} transformation en objets manipulables.
    \item \textbf{Nettoyage :} standardisation et normalisation.
    \item \textbf{Validation :} application des règles métier.
    \item \textbf{Sortie :}
    \begin{itemize}
        \item Données valides → persistance.
        \item Données invalides → rapport d’erreurs.
    \end{itemize}
\end{itemize}
