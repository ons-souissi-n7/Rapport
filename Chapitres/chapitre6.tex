\section{Stratégie de validation}

% ─────────────────────────────────────────────────────────────

La stratégie de validation repose sur plusieurs niveaux complémentaires.

Le premier niveau regroupe les tests unitaires, qui vérifient une règle de gestion ou un service isolé, et les tests d'intégration, qui vérifient le comportement réel des endpoints REST une fois connectés à la base de données.

Le deuxième niveau concerne les tests de composants frontend. Ceux-ci vérifient le comportement d'un composant ou d'une interface utilisateur pris isolément, sans faire tourner l'application complète.

Enfin, les tests End-to-End permettent de valider certains parcours complets à travers la stack applicative. Ils vérifient ainsi l'interaction entre le frontend, le backend, la base de données et le mécanisme d'authentification utilisé dans l'environnement de test.

Cette stratégie est complétée par des tests spécifiques relatifs à la sécurité, ainsi que par des scripts de performance et de charge implémentés avec \texttt{k6}.

\label{sec:e2e-global}

\section{Alertes et tâches asynchrones}

% ─────────────────────────────────────────────────────────────

Certaines fonctionnalités du système reposent sur des traitements asynchrones ou sur la génération d'alertes.

Le déclenchement d'une alerte lorsqu'un administrateur tente de lancer une affectation sans vœu disponible est couvert par un scénario End-to-End dédié. Le calcul d'affectation est quant à lui validé à travers les tests de l'algorithme et des endpoints associés.

Les autres traitements asynchrones, notamment ceux liés aux synchronisations et aux recalculs automatiques, sont principalement couverts indirectement par les tests des services qui leur sont associés. Aucun scénario End-to-End spécifique n'a été identifié pour chacun de ces traitements.

% ─────────────────────────────────────────────────────────────

\section{Statistiques et tableaux de bord}

% ─────────────────────────────────────────────────────────────

Les indicateurs statistiques du système sont calculés à partir des données de mobilité et des résultats d'affectation. Les endpoints responsables de ces agrégations sont couverts par des tests backend.

La génération des exports Excel associés est également testée. Le chargement de la page des tableaux de bord analytiques est inclus dans le parcours administrateur End-to-End. Toutefois, les différents filtres proposés dans l'interface ne sont pas tous couverts par des scénarios dédiés.

Le calcul de la durée cumulée de mobilité CTI suit une approche similaire. Les calculs et les exports associés sont couverts côté API, tandis que les interfaces de consultation et de téléchargement ne disposent pas de la même profondeur de couverture.

\section{Validation de la sécurité}

% ─────────────────────────────────────────────────────────────

La sécurité applicative dispose d'une suite de tests spécifique composée de 42 tests. Ces tests couvrent notamment :

\begin{itemize}

    \item l'accès aux ressources sans authentification ;
    
    \item l'utilisation d'un jeton expiré ;
    
    \item l'utilisation d'un jeton invalide ou altéré ;
    
    \item la tentative d'accès d'un étudiant à des ressources administratives ;
    
    \item la tentative d'accès d'un étudiant aux données d'un autre étudiant ;
    
    \item l'accès autorisé pour un administrateur ;
    
    \item l'authentification reposant sur les cookies ;
    
    \item les endpoints volontairement publics.

\end{itemize}

Ces tests permettent de valider les principaux mécanismes d'authentification et de contrôle d'accès implémentés dans l'application.

En revanche, aucun test spécifique d'injection SQL, de XSS ou de CSRF n'a été identifié dans les artefacts de tests disponibles.

Le pipeline d'intégration continue complète cette validation par un scan de vulnérabilités des images Docker avec Trivy. Les vulnérabilités de sévérité élevée ou critique peuvent bloquer le pipeline.

% ─────────────────────────────────────────────────────────────

\section{Performance et charge}

% ─────────────────────────────────────────────────────────────

Deux scripts \texttt{k6} ont été implémentés pour évaluer les performances de l'application.

Le premier correspond à un test de charge ciblant les endpoints les plus sollicités et permettant de mesurer notamment les temps de réponse et les taux d'erreur sous une charge concurrente.

Le second constitue un test plus simple permettant de vérifier le comportement général de l'API.

Ces scripts sont exécutables, mais les résultats détaillés d'une campagne de test complète ne sont pas disponibles dans les éléments analysés. Il n'est donc pas possible de conclure quantitativement au respect des objectifs de performance définis pour le système.

Des tests complémentaires mesurent également certains temps de réponse directement à l'aide du client de test Django. Ces mesures permettent de détecter certaines régressions, mais ne remplacent pas une véritable mesure réalisée sous charge concurrente.

% ─────────────────────────────────────────────────────────────

\section{Intégration continue et conteneurisation}

% ─────────────────────────────────────────────────────────────

Le pipeline d'intégration continue automatise plusieurs étapes de validation du système.

Il comprend notamment :

\begin{itemize}

    \item l'analyse statique et la vérification du format du code backend (\texttt{ruff}) ;

    \item l'exécution des tests backend avec une base PostgreSQL ;

    \item la vérification du seuil minimal de couverture backend ;

    \item l'analyse statique et la vérification des types du code frontend (ESLint, TypeScript) ;

    \item l'exécution des tests frontend ;

    \item la construction des images Docker ;

    \item l'analyse des vulnérabilités des images avec Trivy.

\end{itemize}

La suite End-to-End Playwright reste indépendante de ce pipeline principal et doit être exécutée séparément.

Le déploiement dans l'environnement cible s'appuie sur les conteneurs Docker et comprend notamment la récupération du code, la reconstruction des services, l'application des migrations de la base de données et la collecte des fichiers statiques.

\section{Analyse de qualité de code}

% ─────────────────────────────────────────────────────────────

Une instance SonarQube est disponible dans l'environnement de développement, avec une configuration dédiée au projet (périmètre analysé, exclusions, rapports de couverture backend et frontend). Son usage reste local : l'analyse est lancée manuellement, en dehors du pipeline d'intégration continue.

Le typage statique du backend, préparé avec \texttt{mypy} et \texttt{django-stubs}, est configuré mais n'est pour l'instant appelé ni localement ni dans le pipeline CI.

\section*{Conclusion}

\justifying

\phantomsection

\addcontentsline{toc}{section}{Conclusion}

La validation montre une couvxerture solide sur le cœur du système (cycle de vie de l'année universitaire, algorithme d'affectation, contrôle d'accès) et plus partielle sur les flux réels d'upload et de téléchargement ainsi que sur les besoins non fonctionnels de performance et de disponibilité.
